## Unresolved at-rest encryption clarification

Independently checked the current [canonical Handling Requirements](https://developer.chrome.com/docs/webstore/program-policies/policies), [official User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq), and [Storage API guidance](https://developer.chrome.com/docs/extensions/reference/api/storage?hl=en) on October 3. The canonical policy requires secure handling of any collected user data and modern cryptography for transmission, without separately specifying local AES/RSA storage. FAQ Q9 expressly specifies strong at-rest encryption, while Q8 emphasizes the transmission minimum. Q3/Q4 include locally handled URLs and user-created content; avoiding financial or authentication collection does not establish an exemption. The API recommends memory-only `storage.session` for sensitive information but does not certify a persistent-storage policy exemption.

QuickLaunch currently persists ordinary JSON in Chrome local storage, including snippets and unfinished drafts. Optional clipboard expansion is temporary and is not persisted. The public policy accurately discloses unencrypted storage. That disclosure, browser profile isolation, optional OS disk encryption, or a warning against storing secrets does not establish compliance with Q9. No authoritative local-only carveout was found. This is a material unresolved applicability question, not proof of Google rejection or evidence of an exploitable vulnerability.

Obtain authoritative Chrome Web Store clarification for this precise use case, or design and test encryption with meaningful key management, migration, backup/restore and worker-restart behavior before declaring the gate complete. Storing an unprotected key beside ciphertext or merely changing disclosure text would not establish meaningful at-rest protection. No encryption code or storage migration was added in this follow-up.

The user's later instruction explicitly authorizes submission **for review**. That action is separate from certifying this unresolved requirement or publishing to users. The [official publication workflow](https://developer.chrome.com/docs/webstore/publish) supports deferred publishing after review, and the [review process](https://developer.chrome.com/docs/webstore/review-process) evaluates compliance and can reject a submission. After functional/package checks, a transparent review submission with deferred publication may proceed. Keep the unencrypted-storage disclosure accurate; do not affirm an encryption statement that the candidate cannot substantiate. A review outcome must not be reported as a general published exemption. The earlier hold was a conservative recommendation, not evidence of an established rejection.
